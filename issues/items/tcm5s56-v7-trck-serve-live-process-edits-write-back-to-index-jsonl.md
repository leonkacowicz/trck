# serve: a live process over the tracker ref, with writes from the page

## Summary
`trck html` emits a static page — a JSON island plus the compiled-in `assets/app.js`,
regenerated by hand whenever the tracker moves. `serve` keeps a process alive behind that page,
so it reads a tracker that moves, and writes back to it.

The frontend is already most of the way there. `app.js` stages edits (`state.edits`,
`commandFor`, `pendingCommands`) and renders the `trck` commands you would then have to run by
hand. `serve` replaces that panel's copy-button with a POST that builds the same `Op` in-process.

**Why this waits on #sqzr7nk.** A `serve` that wrote *today* would write into `issues/` in
whatever checkout it was launched from — dirtying the tree while you work, on whatever branch you
happen to be on. That is exactly the coupling the worktree ritual exists to avoid, and it is why
this issue has sat at `low` with an empty body since it was filed. Once writes are `hash-object`
→ `write-tree` → `commit-tree` → `update-ref` → `push` against `trck-issues`, a served process
touches no working tree at all: safe on a dirty checkout, on any branch, with nothing to clean up.

That inverts the issue. Before the flip `serve` is a footgun; after it, it is the only frontend
that can write.

## Acceptance criteria
- [ ] `trck serve [--port N]` binds **loopback only** and serves the page `html` already emits.
- [ ] Writes from the page go through `finalize` → `Changeset`/`Op` → the git backend — the same
      seam the CLI uses, called in-process. The server never shells out to itself.
- [ ] No parsed index is held across requests, or it is cached keyed on the ref SHA: another
      `trck` in another terminal moving the local ref is normal for a long-lived process and
      impossible for every other verb.
- [ ] A poll loop fetches and applies the ahead / equal / behind / diverged rule from #abynj5c,
      fast-forwarding when behind.
- [ ] Ref movement — local or remote — pushes a re-render to open pages.
- [ ] Pending (unpushed) commits are visible in the UI, and `sync` is reachable from it.
- [ ] Body editing goes through the same path as `trck edit` (#zxz9vu2).
- [ ] Conformance covers the verb's startup contract and its refusal cases; the request/response
      layer is unit-tested.

## Notes

### The auto-fetch exception
#sqzr7nk states that **reads must not auto-fetch** — too slow, and it makes every read need the
network. `serve` breaks that rule deliberately: it is a long-lived process with a timer rather
than a verb in a pipeline, and a page left open on a week-old ref is the time-travel bug in a new
costume. Write it down as a stated exception, so it does not read as drift later.

### It makes the op trailer load-bearing
The `Trck-Op` trailer (#93zhqbd) and stacked replay (#9gxktnk) cover a case that is rare for a
one-shot verb — several pending commits while the remote has moved. For a browser tab left open
on a flaky network it is routine. `serve` is also the first place pending state has somewhere to
live: a badge in the UI, instead of a line printed once and lost.

### The HTTP layer
std has no HTTP server, so this is either hand-rolled HTTP/1.1 over `TcpListener` plus a thread
pool, or a crate. **The dependency rule no longer forbids the crate** — the constraint is one
self-contained binary, so anything that links statically qualifies. Decide it on build cost and
supply-chain surface, not on a prohibition.

Either way this is the binary's first listening socket. Loopback-only, and said in the help text
rather than left implied.

For live updates, server-sent events over a held-open connection beat polling from the browser:
one timer instead of two, on a socket the server already holds.

### Worth stating rather than discovering
A button in a browser that closes an issue is a one-click write to a shared remote branch with no
review step. That is fine for a tracker, and it is a different posture from a verb that emits a
static file.

### Decomposition
Not filed as children yet. The natural split: the serving layer; the POST-to-`Op` bridge; the
poll and fast-forward loop; SSE and re-render; the pending/sync UI.
