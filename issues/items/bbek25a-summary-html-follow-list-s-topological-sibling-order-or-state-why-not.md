# summary/html: follow list's topological sibling order, or state why not

## Summary
`list` now orders siblings by a global topological rank (`src/query/rank.rs`, from
[[list-order-siblings-by-a-global-topological-rank-blockers-first]]), so a blocker renders above what
it blocks. `SUMMARY.md` and the HTML tree still sort on their own and now disagree with it:

- `src/summary.rs` — `parents.sort_by(id)` and `items.sort_by(priority, then id)`.
- `src/html.rs` — `roots.sort()`, and whatever the compiled-in `assets/app.js` does client-side.

Three coherent answers, and the issue is to pick one rather than leave the three views drifting:

1. **Both follow.** `rank::sibling_rank` is public within the crate and takes any key function, so
   `summary` would pass its priority-then-id key and get the same treatment. Most consistent; makes
   `SUMMARY.md` churn once.
2. **Only the HTML tree follows.** It is a browse view like `list`; `SUMMARY.md` is a report, and a
   report grouped by status arguably wants declared order, not a work order.
3. **Neither follows,** and the difference is documented — `list` is the "what do I do next" view,
   the other two are inventories.

Note that `SUMMARY.md` is regenerated by every mutating verb, so option 1 rewrites it on the next
write regardless of when it lands.

## Acceptance criteria
- [ ] A decision recorded here, with the reason.
- [ ] If either view follows: it calls `rank::sibling_rank` rather than growing a second ordering,
      and its conformance goldens are updated in the same change.
- [ ] If neither does: the README says which view is ordered how, so the difference reads as a
      choice rather than an oversight.

## Notes
- The HTML view has a second ordering in `assets/app.js`, which is a compiled-in string — any change
  there needs a case in `tests/app_js.rs`, since nothing else would catch a syntax error in it.
- Cheap either way: the rank is a `BTreeMap<String, usize>` lookup once the graph is loaded.
